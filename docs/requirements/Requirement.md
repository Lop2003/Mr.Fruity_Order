## Requirement: Store-specific Product Mapping

### สถานะงานปัจจุบัน

ตอนนี้ยังไม่ต้องแก้ชื่อสินค้า “ถั่วงอก” และยังไม่ต้องแก้ไขโค้ด

ขั้นตอนแรกให้ตรวจสอบ requirement วิเคราะห์ผลกระทบ และยืนยันความเข้าใจก่อนเริ่ม implementation หากพบข้อกำกวมให้สอบถามก่อน ห้ามตั้งสมมติฐานเองในส่วนที่มีผลต่อการรับออเดอร์หรือการตัดสต๊อก

---

## 1. โครงสร้างชีต StoreMapping

ชีต `StoreMapping` มีโครงสร้างดังนี้:

| คอลัมน์ | ข้อมูล                    |
| ------- | ------------------------- |
| A       | ชื่อร้าน                  |
| B       | ชื่อสินค้าที่ได้รับจาก PO |
| C       | ชื่อสินค้ามาตรฐานในระบบ   |

คู่ค่าที่ใช้เป็น lookup key คือ:

```text
ชื่อร้าน + ชื่อสินค้าใน PO
```

การค้นหาใน `StoreMapping` ต้องเป็น exact mapping ห้ามใช้ fuzzy matching ภายใน StoreMapping

---

## 2. ขอบเขตร้านค้า

ข้อมูลใน `StoreMapping` รอบแรกมีเฉพาะสามร้าน:

* Dusit Thani
* Rhapsody
* Getfresh

ห้าม hardcode ชื่อร้านทั้งสามใน source code

ระบบต้องทำงานแบบ data-driven:

* ร้านที่มีข้อมูลอยู่ใน `StoreMapping` ให้ใช้ StoreMapping เป็นลำดับแรก
* ร้านที่ไม่มีข้อมูลอยู่ใน `StoreMapping` ให้ข้ามขั้นตอนนี้และเข้าสู่ flow เดิมทันที
* หากอนาคตเพิ่มร้านใหม่เข้า StoreMapping ระบบต้องรองรับได้โดยไม่ต้องแก้โค้ด

ดังนั้น “ใช้เฉพาะสามร้าน” หมายถึงขอบเขตข้อมูลใน StoreMapping ปัจจุบัน ไม่ใช่เงื่อนไขที่ต้องเขียนชื่อร้านไว้ในโค้ด

---

## 3. ลำดับการค้นหา Mapping

### ร้านที่มีข้อมูลใน StoreMapping

ใช้ลำดับดังนี้:

```text
StoreMapping → Mapping เดิม → Fuzzy matching → NOT_FOUND
```

### ร้านที่ไม่มีข้อมูลใน StoreMapping

ใช้ flow เดิมโดยไม่มีการเปลี่ยนแปลง:

```text
Mapping เดิม → Fuzzy matching → NOT_FOUND
```

StoreMapping ต้องมีลำดับความสำคัญสูงกว่า Mapping เดิมเสมอ

ตัวอย่าง:

```text
ร้าน: Dusit Thani
ชื่อสินค้าใน PO: ถั่วงอก

StoreMapping ชี้ไปสินค้า A
Mapping เดิมชี้ไปสินค้า B

ผลลัพธ์ที่ถูกต้อง: ต้องใช้สินค้า A จาก StoreMapping
```

---

## 4. กรณีพบข้อมูลใน StoreMapping

เมื่อพบคู่ `ชื่อร้าน + ชื่อสินค้าใน PO` ใน StoreMapping:

* ถือว่าเป็น mapping ที่ได้รับการอนุมัติแล้ว
* สามารถรับออเดอร์ได้
* สามารถตัดสต๊อกอัตโนมัติได้ หากข้อมูลปลายทางถูกต้องและสต๊อกเพียงพอ
* ไม่แสดงเครื่องหมาย `🔍 จับคู่ชื่ออัตโนมัติ`
* บันทึกแหล่งที่จับคู่เป็น `STORE_MAPPING`

อย่างไรก็ตาม ต้องตรวจสอบความถูกต้องของชื่อมาตรฐานก่อนตัดสต๊อกทุกครั้งตามข้อถัดไป

---

## 5. การตรวจสอบชื่อมาตรฐาน

ค่าชื่อมาตรฐานจาก `StoreMapping` คอลัมน์ C ต้องมีอยู่ใน `Mapping` คอลัมน์ B แบบตรงกัน

หากไม่พบชื่อดังกล่าวใน Mapping คอลัมน์ B:

* ถือว่า StoreMapping แถวนั้นไม่ถูกต้อง
* ห้ามตัดสต๊อกอัตโนมัติสำหรับรายการนั้น
* แสดงสถานะ `ต้องตรวจสอบ`
* บันทึก Log ว่า `StoreMapping ไม่ถูกต้อง`
* ระบุชื่อร้าน ชื่อจาก PO และชื่อมาตรฐานที่ตรวจสอบไม่พบ
* ห้าม fallback ไปเลือกสินค้าจาก Mapping เดิมหรือ fuzzy matching เพื่อกลบ configuration ที่ผิด

ตัวอย่าง:

```text
StoreMapping:
Dusit Thani | ถั่วงอก | ถั่วงอกจีน

แต่ Mapping คอลัมน์ B ไม่มีคำว่า “ถั่วงอกจีน”

ผลลัพธ์:
- ห้ามตัดสต๊อก
- รายการต้องอยู่ในสถานะ “ต้องตรวจสอบ”
- Log เป็น source: STORE_MAPPING
- Log ระบุเหตุผลว่าไม่พบชื่อมาตรฐานใน Mapping
```

---

## 6. กรณีไม่พบข้อมูลใน StoreMapping

หากไม่พบคู่ `ชื่อร้าน + ชื่อสินค้าใน PO`:

* ให้ใช้ flow เดิมต่อทันที
* ตรวจ Mapping เดิม
* หากไม่พบ ให้ทำ fuzzy matching
* หากยังไม่พบ ให้เป็น `NOT_FOUND`

พฤติกรรม UX การรับออเดอร์ และการตัดสต๊อกของ flow เดิมต้องไม่เปลี่ยนแปลง

---

## 7. ข้อมูล StoreMapping ซ้ำหรือขัดแย้ง

หากพบคู่ `ชื่อร้าน + ชื่อสินค้าใน PO` ซ้ำหลายแถว:

### ชี้ไปชื่อมาตรฐานเดียวกัน

สามารถถือเป็น mapping เดียวกันได้ แต่ควรบันทึกหรือรายงานข้อมูลซ้ำเพื่อให้แก้ไขข้อมูลต้นทางภายหลัง

### ชี้ไปคนละชื่อมาตรฐาน

ถือเป็น conflicting mapping และต้อง:

* หยุดประมวลผลเฉพาะรายการนั้น
* ห้ามเลือกสินค้าเอง
* ห้ามตัดสต๊อก
* แสดงสถานะ `ต้องตรวจสอบ`
* บันทึก Log พร้อมรายละเอียดชื่อมาตรฐานทั้งหมดที่ขัดแย้งกัน

---

## 8. Performance

ภายในหนึ่งรอบการประมวลผลออเดอร์หรือไฟล์ PO:

* อ่าน `StoreMapping` เพียงครั้งเดียว
* สร้าง lookup structure ไว้ใน memory โดยใช้ `ชื่อร้าน + ชื่อสินค้าใน PO` เป็น key
* ห้ามอ่าน Google Sheet ใหม่แยกตามสินค้าแต่ละรายการ
* สามารถโหลดข้อมูลใหม่เมื่อเริ่มรอบการประมวลผลครั้งถัดไปได้

ตัวอย่าง:

```text
PO มีสินค้า 100 รายการ

พฤติกรรมที่ถูกต้อง:
อ่าน StoreMapping 1 ครั้ง แล้วค้นหาจากข้อมูลใน memory 100 ครั้ง

พฤติกรรมที่ห้าม:
เรียก Google Sheets 100 ครั้ง
```

---

## 9. UX

UX เดิมต้องเหมือนเดิมทั้งหมด ยกเว้นกรณีต่อไปนี้:

* รายการที่จับคู่สำเร็จผ่าน StoreMapping ไม่แสดง `🔍 จับคู่ชื่ออัตโนมัติ`
* รายการที่ StoreMapping ผิดหรือขัดแย้งกันต้องแสดงสถานะ `ต้องตรวจสอบ`

รายการที่จับคู่ผ่าน `MAPPING`, `FUZZY` หรือ `NOT_FOUND` ต้องคงพฤติกรรมและการแสดงผลเดิม

ร้านที่ไม่มีข้อมูลใน StoreMapping ต้องไม่เห็นความเปลี่ยนแปลงใด ๆ

---

## 10. Logging

แต่ละรายการต้องบันทึกข้อมูลอย่างน้อยดังนี้:

* ชื่อร้าน
* ชื่อสินค้าจาก PO
* ชื่อมาตรฐานที่จับคู่ได้ หากมี
* แหล่งที่ใช้จับคู่:

  * `STORE_MAPPING`
  * `MAPPING`
  * `FUZZY`
  * `NOT_FOUND`
* ผลการประมวลผล
* เหตุผลที่ต้องตรวจสอบ หากมี

กรณี StoreMapping ผิดหรือข้อมูลขัดแย้ง:

* source ยังคงเป็น `STORE_MAPPING`
* ต้องมี error reason เช่น:

  * `STANDARD_NAME_NOT_FOUND`
  * `CONFLICTING_STORE_MAPPING`

---

## 11. Stock deduction

รายการที่มาจาก StoreMapping สามารถตัดสต๊อกตาม flow ปกติได้เมื่อ:

* StoreMapping ไม่ขัดแย้งกัน
* ชื่อมาตรฐานคอลัมน์ C มีอยู่ใน Mapping คอลัมน์ B
* พบสินค้าที่เกี่ยวข้องในระบบ
* สต๊อกเพียงพอ
* ผ่าน validation เดิมทั้งหมด

StoreMapping ต้องไม่ข้าม validation เรื่องจำนวนสต๊อก และต้องไม่ทำให้เกิดการตัดสต๊อกซ้ำเมื่อประมวลผลออเดอร์เดิมหลายครั้ง

---

## 12. Test cases ที่ต้องครอบคลุม

ต้องทดสอบอย่างน้อยกรณีต่อไปนี้:

1. Dusit Thani จับคู่สำเร็จผ่าน StoreMapping
2. Rhapsody จับคู่สำเร็จผ่าน StoreMapping
3. Getfresh จับคู่สำเร็จผ่าน StoreMapping
4. ชื่อเดียวกันมีทั้ง StoreMapping และ Mapping เดิม โดยต้องเลือก StoreMapping
5. ร้านมีข้อมูลใน StoreMapping แต่สินค้าบางรายการไม่มี mapping และต้อง fallback เข้า flow เดิม
6. ร้านที่ไม่มีข้อมูลใน StoreMapping ต้องใช้ flow เดิมทั้งหมด
7. ชื่อมาตรฐานคอลัมน์ C ไม่มีใน Mapping คอลัมน์ B
8. คู่ร้านและชื่อ PO ซ้ำแต่ชี้ไปคนละสินค้า
9. คู่ร้านและชื่อ PO ซ้ำและชี้ไปสินค้าเดียวกัน
10. สินค้าจับคู่สำเร็จแต่สต๊อกไม่พอ
11. การประมวลผลหรือตัดสต๊อกออเดอร์เดิมหลายรอบ
12. หลายสินค้าใน PO เดียวกัน โดย StoreMapping ต้องถูกอ่านเพียงครั้งเดียว
13. ตรวจว่า StoreMapping ไม่แสดงเครื่องหมาย `🔍 จับคู่ชื่ออัตโนมัติ`
14. ตรวจ regression ของ Mapping เดิม, fuzzy matching และ NOT_FOUND
15. ตรวจ Log ของทุกแหล่งการจับคู่และทุกกรณีผิดพลาด

## 13. Acceptance criteria

งานถือว่าเสร็จเมื่อ:

* ลำดับการจับคู่ถูกต้องตาม requirement
* ไม่มีการ hardcode ชื่อร้าน
* StoreMapping ถูกอ่านเพียงครั้งเดียวต่อรอบการประมวลผล
* StoreMapping ที่ผิดหรือขัดแย้งกันไม่สามารถตัดสต๊อกได้
* ไม่มีการเลือกสินค้าเองเมื่อข้อมูลกำกวม
* ร้านอื่นยังใช้ flow เดิมโดยไม่มี regression
* UX แตกต่างเฉพาะรายการที่จับคู่ผ่าน StoreMapping
* Log แสดงแหล่งที่จับคู่และสาเหตุผิดพลาดครบ
* การตัดสต๊อกหลายรอบไม่ทำให้สต๊อกถูกหักซ้ำ
* Tests, lint, typecheck และ build ที่เกี่ยวข้องผ่านทั้งหมด

ก่อนเริ่มแก้โค้ด ให้สรุปความเข้าใจ ระบุไฟล์หรือ flow ที่คาดว่าจะได้รับผลกระทบ เสนอแผน implementation และแจ้งข้อสงสัยที่ยังต้องยืนยันก่อน
